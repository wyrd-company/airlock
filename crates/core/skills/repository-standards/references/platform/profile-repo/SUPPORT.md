# Support

## Before opening anything

Read the repository's `README.md` and anything under `docs/`. Most questions
about installing, configuring, or running a tool are answered there, and a gap
in that documentation is itself worth reporting.

## Where to go

| You have                          | Use                                         |
| --------------------------------- | ------------------------------------------- |
| A reproducible bug                | A **bug report** issue                      |
| A suggestion                      | An **idea** issue                           |
| A security vulnerability          | The **Security** tab — never a public issue |
| A change you have already written | A pull request                              |

## What a good report looks like

Say what you expected, what happened instead, and the shortest sequence that
reproduces it. Include the version and the platform. A report that someone else
can reproduce gets fixed; a report that cannot be reproduced usually cannot be
acted on at all.

## What to expect

These are small projects maintained by a small team. Issues are read, and
answered when there is something useful to say. An idea may sit while it is
considered against work already planned — silence is not rejection, but it is
also not a commitment.

Work is planned and tracked outside GitHub, so an issue staying open does not
mean nothing is happening, and an issue closing does not always mean the
underlying need was dismissed. The closing comment will say which it is.
